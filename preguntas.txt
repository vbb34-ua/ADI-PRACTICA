BLOQUE 1: LAS 4 PREGUNTAS CLAVE DEL MINI-TEST (IMPRESCINDIBLES)
================================================================================

PREGUNTA 1:
¿En que iteracion se implementa la autenticacion con JWT y gestion de perfiles?
RESPUESTA:
En la Iteracion 02 ("02-autenticacion-y-perfiles.md"). En esta fase se implemento 
authService.js, cubriendo el registro, login con emision de JWT, logout, consulta 
y modificacion de perfil de usuario.

PREGUNTA 2:
¿Quien genera el token JWT y en que momento exacto se produce?
RESPUESTA:
El token JWT lo genera el servidor de autenticacion de Supabase (GoTrue / Supabase Auth)
en el backend. Se produce en el momento en que el usuario se autentica con exito 
mediante sus credenciales (email y password) a traves de la funcion 
supabase.auth.signInWithPassword (o al registrarse con supabase.auth.signUp).

PREGUNTA 3:
¿Donde y como se le envia el token JWT al cliente, y como se envia en peticiones posteriores?
RESPUESTA:
- Envio al cliente: El servidor GoTrue envia el token en el cuerpo de la respuesta 
  JSON de la peticion HTTP de login, concretamente en la propiedad:
  data.session.access_token (junto con su refresh_token y metadatos).
- Peticiones posteriores: El cliente almacena ese token y lo adjunta en la cabecera 
  HTTP de autorizacion de cada solicitud:
  Authorization: Bearer <access_token>
  El SDK de Supabase (@supabase/supabase-js) automatiza este envio en todas las 
  consultas a PostgREST y llamadas a la base de datos.

PREGUNTA 4:
¿Como se asegura que un usuario no pueda editar o borrar el perfil o torneo de otro usuario?
RESPUESTA:
Mediante Row Level Security (RLS) a nivel de motor de base de datos en PostgreSQL:
- En la tabla "perfiles": la politica UPDATE valida que (auth.uid() = id).
- En la tabla "torneos": las politicas UPDATE y DELETE validan que 
  (auth.uid() = organizador_id).
Adicionalmente, en la Capa de Servicios JavaScript (torneoService y authService) 
se realiza una comprobacion defensiva previa comparando el id del usuario 
autenticado antes de emitir la orden a la base de datos.

BLOQUE 2: AUTENTICACION, TOKENS JWT Y SEGURIDAD (RLS)
================================================================================

PREGUNTA 5:
¿Que es un token JWT y cual es su estructura interna?
RESPUESTA:
Un JWT (JSON Web Token) es un estandar abierto (RFC 7519) para transmitir informacion 
segura y compacta entre partes en formato JSON de forma verificable.
Consta de tres partes codificadas en Base64Url y separadas por puntos (header.payload.signature):
1. Header (Encabezado): tipo de token (JWT) y algoritmo de firma (ej. HS256 o RS256).
2. Payload (Carga util): contiene los "claims" o afirmaciones sobre el usuario 
   (sub/uid, email, rol, fecha de expiracion exp, etc.).
3. Signature (Firma digital): hash criptografico generado con la clave secreta 
   del servidor, que certifica que el token no ha sido alterado por intermediarios.

PREGUNTA 6:
¿Cual es la diferencia fundamental entre Autenticacion y Autorizacion?
RESPUESTA:
- Autenticacion: Es el proceso de verificar la IDENTIDAD del usuario (¿Quien eres?). 
  Se resuelve cuando el usuario aporta sus credenciales validas y obtiene su JWT.
- Autorizacion: Es el proceso de verificar los PERMISOS del usuario identificado 
  (¿Que puedes hacer?). Determina si un usuario autenticado tiene derecho a leer, 
  crear, modificar o borrar un recurso concreto (ej. solo el capitan puede inscribir 
  a su equipo, solo el organizador puede cancelar su torneo).

PREGUNTA 7:
¿Que significa RLS (Row Level Security) y por que es tan importante en arquitecturas BaaS?
RESPUESTA:
RLS es una funcionalidad nativa del motor PostgreSQL que filtra las filas que un usuario 
puede consultar o modificar en una tabla basandose en politicas SQL.
En arquitecturas BaaS (donde el cliente consulta directamente la API PostgREST de Supabase), 
RLS es la barrera definitiva de seguridad: aunque un usuario malintencionado intente 
hacer un UPDATE manual via HTTP cambiando el ID de un torneo ajeno, el propio motor 
PostgreSQL descarta la operacion porque auth.uid() no coincide con organizador_id.

PREGUNTA 8:
¿Cual es la diferencia entre USING y WITH CHECK en las politicas RLS de PostgreSQL?
RESPUESTA:
- USING: Se aplica a operaciones SELECT, UPDATE y DELETE. Evalua si las filas ya 
  existentes en la base de datos son visibles o modificables para el usuario.
- WITH CHECK: Se aplica a operaciones INSERT y UPDATE. Evalua si las nuevas filas 
  que se van a insertar o los nuevos datos resultantes cumplen la condicion permitida 
  (por ejemplo, que el organizador_id del torneo nuevo sea igual a auth.uid()).

PREGUNTA 9:
¿Por que no se almacenan las contraseñas en texto plano en la base de datos?
RESPUESTA:
Por seguridad critica: si la base de datos se ve comprometida, las contraseñas 
quedarian expuestas. Supabase Auth (GoTrue) almacena las contraseñas hasheadas 
con algoritmos criptograficos lentos con salting (bcrypt/argon2), haciendo inviables 
los ataques de diccionario y tablas rainbow.

BLOQUE 3: ARQUITECTURA DE LA APLICACION Y TECNOLOGIAS (BaaS / SUPABASE)
================================================================================

PREGUNTA 10:
¿Que tipo de arquitectura se ha implementado en la Practica 1?
RESPUESTA:
Una arquitectura Backend-as-a-Service (BaaS) desacoplada:
1. Nivel de Persistencia y Auth: Supabase Cloud / Local (PostgreSQL 15+, GoTrue, PostgREST).
2. Nivel de Conexion: Cliente singleton inicializado en src/lib/supabaseClient.js.
3. Capa de Servicios de Negocio: Modulos puros JavaScript en src/services/ que 
   encapsulan la logica, validaciones y acceso a datos.
4. Nivel de Consumo / Pruebas: Suite automatizada en Vitest (y futuro frontend en P2).

PREGUNTA 11:
¿Por que se crea una Capa de Servicios desacoplada en lugar de llamar a Supabase directamente?
RESPUESTA:
Por 4 razones clave de ingenieria de software:
1. Desacoplamiento e inversion de dependencias: El cliente o consumidor no conoce 
   la sintaxis interna de Supabase; si el dia de mañana se migra a Firebase o a una API 
   propia Express, la interfaz del servicio se mantiene intacta.
2. Centralizacion de reglas de negocio: Validaciones previas de formato, rangos de 
   titulos, calculo de plazas y sanitizacion de datos se hacen en un unico punto.
3. Testabilidad: Permite mockear las respuestas del backend y probar la logica de 
   negocio sin conexion a la red de forma inmediata y reproducible.
4. Reutilizacion: Toda la aplicacion futura (web, mobile, cli) consumira exactamente 
   las mismas funciones exportadas desde src/services/index.js.

PREGUNTA 12:
¿Que componentes integran la suite de Supabase y que funcion cumple cada uno?
RESPUESTA:
1. PostgreSQL: Base de datos relacional que almacena datos, tipos, constraints y RLS.
2. GoTrue (Supabase Auth): Microservicio en Go que gestiona usuarios, hashes de 
   contraseñas, sesiones y firma de tokens JWT.
3. PostgREST: Servidor web que expone automaticamente cualquier base de datos 
   PostgreSQL como una API RESTful con soporte para filtros, ordenacion y paginacion.
4. Realtime: Servidor basado en Elixir para escuchar cambios mediante WebSockets.
5. Storage: Servicio de almacenamiento de archivos binarios (avatares, logos).

PREGUNTA 13:
¿Por que en la Practica 1 NO se implementa interfaz grafica ni HTML ni CSS?
RESPUESTA:
Porque el enunciado y la especificacion de la Practica 1 establecen estrictamente 
que el alcance se limita al diseño de la base de datos, la capa de servicios backend 
y su validacion mediante pruebas automatizadas. La interfaz grafica completa 
(HTML, CSS, vistas) esta planificada para la Practica 2.

BLOQUE 4: MODELO DE DATOS, POSTGRESQL, TRIGGERS Y CONSTRAINTS
================================================================================

PREGUNTA 14:
¿Cual es el Recurso Principal y cuales son los Recursos Secundarios del sistema?
RESPUESTA:
- Recurso Principal: TORNEOS (tabla "torneos"). Representa las competiciones con 
  titulo, videojuego, formato, plazas maximas, fechas y estados.
- Recursos Secundarios:
  1. EQUIPOS (tabla "equipos"): Escuadras creadas y lideradas por un capitan.
  2. INSCRIPCIONES (tabla "inscripciones"): Vinculacion entre un equipo y un torneo (N:M).
  3. PARTIDAS (tabla "partidas"): Enfrentamientos entre dos equipos en un torneo.
  4. PERFILES (tabla "perfiles"): Informacion publica del usuario enlazada a auth.users.

PREGUNTA 15:
¿Como estan relacionadas las entidades en el Diagrama Entidad-Relacion?
RESPUESTA:
- auth.users 1 <---> 1 perfiles (clave foranea id con ON DELETE CASCADE).
- perfiles 1 <---> N torneos (un usuario puede organizar varios torneos).
- perfiles 1 <---> N equipos (un usuario es capitan de sus equipos).
- torneos 1 <---> N inscripciones y equipos 1 <---> N inscripciones.
  Representa una relacion N a M (Muchos a Muchos) entre Torneos y Equipos resuelta 
  mediante la entidad intermedia "inscripciones".
- torneos 1 <---> N partidas (un torneo agrupa sus enfrentamientos).
- equipos 1 <---> N partidas (cada partida relaciona un equipo local y uno visitante).

PREGUNTA 16:
¿Como se evita que un equipo se inscriba dos veces en el mismo torneo?
RESPUESTA:
Mediante una restriccion UNIQUE compuesta en la tabla "inscripciones":
CONSTRAINT uq_torneo_equipo UNIQUE (torneo_id, equipo_id);
Si se intenta insertar una segunda fila con los mismos identificadores, PostgreSQL 
lanza un error de clave unica violada.

PREGUNTA 17:
¿Que triggers PL/pgSQL se han implementado y cual es su cometido?
RESPUESTA:
Se implementaron 2 triggers principales:
1. on_auth_user_created (AFTER INSERT ON auth.users):
   Ejecuta handle_new_user() para insertar automaticamente una fila en public.perfiles 
   con el id recien generado en auth.users y el username extraido de los metadatos o email.
2. tr_check_torneo_cupo (BEFORE INSERT ON public.inscripciones):
   Ejecuta check_torneo_cupo() para verificar antes de admitir la inscripcion:
   a) Que el torneo tenga estado = 'inscripcion_abierta'.
   b) Que el numero actual de inscripciones confirmadas sea menor estricto que plazas_max.
   Si alguna condicion falla, lanza una excepcion SQL (RAISE EXCEPTION).

PREGUNTA 18:
¿Que restricciones CHECK se definieron en las tablas para garantizar integridad?
RESPUESTA:
- torneos: 
  * char_length(titulo) >= 4 AND char_length(titulo) <= 100
  * plazas_max >= 2
  * estado IN ('borrador', 'inscripcion_abierta', 'en_curso', 'finalizado', 'cancelado')
  * formato IN ('eliminacion_directa', 'doble_eliminacion', 'liga', 'suizo')
- equipos:
  * char_length(nombre) >= 3 AND char_length(nombre) <= 50
  * char_length(tag) >= 2 AND char_length(tag) <= 6
- perfiles:
  * rol IN ('jugador', 'organizador', 'admin')
- inscripciones:
  * estado IN ('confirmada', 'en_espera', 'cancelada')
- partidas:
  * resultado_local >= 0, resultado_visitante >= 0
  * estado IN ('pendiente', 'en_juego', 'finalizada')

PREGUNTA 19:
¿Como se implementa la paginacion y el filtrado en torneoService.listarTorneos?
RESPUESTA:
- Paginacion: Recibe page (ej. 1) y pageSize (ej. 10). Calcula los limites de rango:
  const from = (page - 1) * pageSize;
  const to = from + pageSize - 1;
  Aplica el metodo .range(from, to, { count: 'exact' }) del cliente Supabase.
- Filtrado: Aplica condiciones dinamicas sobre la query si se proporcionan:
  if (videojuego) query = query.eq('videojuego', videojuego);
  if (estado) query = query.eq('estado', estado);
- Retorno: Devuelve un objeto paginado con:
  { torneos: data, total: count, page, pageSize, totalPages: Math.ceil(count / pageSize) }

PREGUNTA 20:
¿Como se consulta el Recurso Principal con sus Recursos Secundarios asociados en una sola llamada?
RESPUESTA:
En torneoService.obtenerTorneoPorId(id, opciones), aprovechando las capacidades 
de PostgREST de Supabase para resolver relaciones foraneas en formato JSON anidado:
let selectQuery = '*';
if (opciones.incluirInscripciones) {
  selectQuery += ', inscripciones(id, estado, fecha_inscripcion, equipo:equipos(id, nombre, tag, logo_url))';
}
if (opciones.incluirPartidas) {
  selectQuery += ', partidas(*)';
}
const { data, error } = await supabase.from('torneos').select(selectQuery).eq('id', id).single();

PREGUNTA 21:
¿Cual es el flujo completo de validacion al inscribir un equipo en un torneo?
RESPUESTA:
En inscripcionService.inscribirEquipo({ torneoId, equipoId, capitanId }):
1. Validacion de parametros de entrada (IDs no nulos).
2. Verificacion de Capitan: Consulta el equipo y valida que equipo.capitan_id === capitanId. 
   Si no lo es, lanza error "Acceso denegado: solo el capitan puede inscribir al equipo".
3. Verificacion de Torneo: Consulta el torneo y valida que torneo.estado === 'inscripcion_abierta'.
4. Verificacion de Aforo: Cuenta las inscripciones confirmadas actuales. Si actuales >= plazas_max, 
   lanza error "El torneo ha alcanzado su cupo maximo".
5. Insercion: Inserta la fila en la tabla "inscripciones". Si la base de datos detecta duplicidad, 
   captura el error del constraint UNIQUE y lanza mensaje amigable.

PREGUNTA 22:
¿Que funciones contiene authService.js y que retorna la funcion login?
RESPUESTA:
- Funciones: registro, login, cerrarSesion, obtenerPerfil, actualizarPerfil, obtenerUsuarioActual.
- Retorno de login:
  Devuelve { user: data.user, session: data.session, token: data.session?.access_token }.
  Esto expone explicitamente el JWT para su uso directo en peticiones o comprobacion en tests.

PREGUNTA 23:
¿Que es el archivo src/services/index.js y que patron de diseño implementa?

permitiendo al consumidor importar cualquier servicio con:

BLOQUE 6: METODOLOGIA SDD, ITERACIONES Y CONTROL DE VERSIONES

PREGUNTA 24:
¿Que significa SDD (Specification-Driven Development) y como se ha aplicado?
RESPUESTA:
SDD es una metodologia en la que el desarrollo esta rigurosamente guiado por la especificacion:
1. Primero se redacta la especificacion formal del modulo (SPEC) antes de tirar una linea de codigo.
2. Se traza el plan de ejecucion paso a paso (PLAN).
3. Se diseña la bateria de pruebas con los resultados esperados (TEST_PLAN).
4. Se implementa el codigo y se contrastan los resultados reales con los esperados.
5. Se documenta la interaccion con la IA (AI_LOG) y los commits asociados.
Esto evita desvios en la arquitectura y previene que la IA agregue codigo superfluo.

PREGUNTA 25:
¿Cuales son las 5 secciones obligatorias que componen el documento de cada iteracion?
RESPUESTA:
1. SPEC: Objetivos funcionales, tecnicos y elementos fuera de alcance.
2. PLAN: Pasos concretos de ejecucion secuencial.
3. TEST_PLAN: Tabla de casos de prueba, resultados esperados y resultados obtenidos.
4. AI_LOG: Herramienta, modelo de IA, prompts clave, decisiones y correcciones manuales.
5. COMMITS RELACIONADOS: Hash y mensaje de los commits de Git vinculados a la iteracion.

================================================================================

PREGUNTA 27:
¿Por que se utiliza un Mock de Supabase (mockSupabase.js) en lugar de consultar siempre la nube?
RESPUESTA:
1. Independencia y Modo Offline: Permite ejecutar los 45 tests en el aula o durante la 
   correccion docente sin necesitar conexion a internet ni credenciales activas.
2. Rendimiento y Velocidad: Las 45 pruebas se ejecutan en memoria en menos de 500 ms 
   (frente a los varios segundos que tardaria la latencia de red a Supabase Cloud).
3. Determinismo y Aislamiento: Los tests no dependen del estado previo de una base de 
   datos compartida ni sufren interferencias por modificaciones concurrentes.
4. Gratuidad: No consume limites de cuotas ni peticiones mensuales del plan de Supabase.

PREGUNTA 28:
¿Como estan organizados los tests automatizados y cuantos hay en total?
RESPUESTA:
Hay un total de 45 pruebas automatizadas (100% de exito) divididas en 5 suites:
1. tests/authService.test.js: 10 tests (registro, validaciones de email/password, login JWT, perfiles).
2. tests/torneoService.test.js: 14 tests (creacion, filtros, paginacion, autorizacion organizador).
3. tests/equipoService.test.js: 12 tests (longitud de tag, nombres, capitan, listados).
4. tests/inscripcionService.test.js: 7 tests (validacion cupo, torneo abierto, cancelacion).
5. tests/servicesIndex.test.js: 2 tests (verificacion de integridad del barrel export).

PREGUNTA 29:
¿Que comandos se utilizan para lanzar los tests y medir la cobertura de codigo?
RESPUESTA:
- Ejecucion estandar de todos los tests:
  npm test
- Ejecucion interactiva en modo observador (re-ejecuta al cambiar codigo):
  npm run test:watch
- Generacion de reporte de cobertura de codigo con motor v8:
  npm run test:coverage
  (Alcanza un 84.48% de cobertura global y mas del 94% en funciones de servicios).

BLOQUE 9: SUPUESTOS PRACTICOS DE "LIVE CODING" (MODIFICACIONES EN DIRECTO)
================================================================================

SUPUESTO 1:
"Añade un nuevo campo 'premio_euros' al torneo. ¿Que partes del proyecto debes modificar?"
RESPUESTA:
1. Base de datos (sql/01_schema.sql):
   ALTER TABLE public.torneos ADD COLUMN premio_euros NUMERIC DEFAULT 0 CHECK (premio_euros >= 0);
2. Capa de Servicios (src/services/torneoService.js):
   En crearTorneo(datos, organizadorId):
   if (datos.premio_euros !== undefined && (typeof datos.premio_euros !== 'number' || datos.premio_euros < 0)) {
     throw new Error("El premio debe ser una cantidad numerica igual o superior a cero.");
   }
   Incluir premio_euros en el objeto a insertar.
3. Tests (tests/torneoService.test.js):
   Añadir prueba de creacion con premio valido y prueba con valor negativo esperando excepcion.

SUPUESTO 2:
"Queremos que solo el organizador del torneo pueda cancelar una inscripcion (quitando al capitan). ¿Como lo harias?"
RESPUESTA:
1. En la politica RLS de PostgreSQL (sql/01_schema.sql):
   Modificar la politica "Capitan o organizador cancela inscripcion" para eliminar la 
   clausula OR que comprueba la capitania, dejando unicamente:
   EXISTS (SELECT 1 FROM public.torneos WHERE torneos.id = inscripciones.torneo_id AND torneos.organizador_id = auth.uid())
2. En la capa de servicios (src/services/inscripcionService.js):
   En cancelarInscripcion(inscripcionId, usuarioId):
   Eliminar la comprobacion de esCapitan y exigir exclusivamente:
   if (inscripcion.torneo.organizador_id !== usuarioId) {
     throw new Error("Acceso denegado: solo el organizador del torneo puede cancelar una inscripcion.");
   }

SUPUESTO 3:
"¿Como forzarias que la contraseña en authService.registro tenga que contener al menos una mayuscula y un digito?"
RESPUESTA:
En src/services/authService.js, dentro de la funcion registro:
const tieneMayuscula = /[A-Z]/.test(password);
const tieneNumero = /[0-9]/.test(password);
if (!tieneMayuscula || !tieneNumero) {
  throw new Error("La contraseña debe contener al menos una letra mayuscula y un numero.");
}

SUPUESTO 4:
